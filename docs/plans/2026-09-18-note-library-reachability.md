## 0. 结论先说

**这不是「扩容」问题，是两件更便宜的事**：①**别静默截断**——文案写着「全部笔记（最近 200 条）」，而 200 条以外**没有任何提示**，用户既不知道有更早的笔记，也不知道去哪找；②**让笔记可检索**——笔记库现在只能逐组折叠/展开扫，而侧栏搜索**只搜课程**。

**为什么现在做**：真实库实测 **3 条笔记**（3 个课时 / 6 行 note 版本）、24 个课时、8 条任务——**200 的上限今天根本碰不到**。所以紧迫性不在上限，而在：

- **诚实性**：静默丢弃用户数据（哪怕只是"不显示"）与仓库的声明层纪律同族——文案必须写能核对的事实。今天 3 条，下学期 3 门课 × 16 讲 = 48 条，再往后就是真问题。
- **可发现性**：笔记一多，「找某节课的笔记」这件事现在**没有第二条路径**——侧栏课程树能到课时，但你得先知道是哪门课；笔记库是唯一的全局入口，而它只能扫。

**这一版要做的**：把 `notes:list` 的返回从「最多 200 行的数组」变成「能如实告知总数 + 能按关键词过滤」的契约，笔记库加一个搜索框，截断时给出路；任务列表（`LIMIT 50`）同类问题一并收口。**不做**虚拟滚动、不做笔记全文检索（`note_json` 里搜正文）、不做笔记库的筛选/排序面板。

## 1. 现状（实测 + 读码）

### 1.1 三条列表都有静默截断

| 位置 | 上限 | 界面文案 | 被截断时的提示 |
|---|---|---|---|
| `notes:list`（`src/main/ipc.ts:1090-1116`） | `LIMIT 200` | 「全部笔记（**最近 200 条**）— 点击一条即可查看与追问」（`NoteViewer.tsx:338`） | **无**（且文案里的 200 是硬编码，改上限不会跟着改） |
| `tasks:list`（`ipc.ts:886-887`） | `LIMIT 50` | 「全部任务（**最近 50 条**）」（`TaskPanel.tsx:122`） | **无**（同样是硬编码） |
| `qa:list` / `qa:recent`（`ipc.ts:1605`、`1625`） | `LIMIT 50` | 无标题 | **无** |

三条都是「按 created_at DESC 取最近 N 条」，**没有任何 offset/过滤参数**，返回纯数组——所以渲染层**无法知道**自己拿到的是不是全量。

### 1.2 笔记库只有「扫」，没有「找」

- `NoteLibrary.tsx`：按「课程名 · 教师」分组、可折叠、每行是课时名 + v 徽标 + 时间戳；组头有「导出 Obsidian」「升级旧笔记」。**没有搜索框、没有筛选、没有排序**。
- 侧栏搜索（`App.tsx` 的 `search-input`）走 `shared/course-search.ts` 的 `courseMatchesQuery`——**只作用于课程树**，不碰笔记。
- 也就是说：想知道「我哪些课有笔记」要靠笔记库扫；想找「第 7 讲的笔记」也要在笔记库里扫（课程树那条路要求先记得是哪门课）。

### 1.3 真实库规模（只读探针）

```
courses 1654 · lessons 24 · notes 6 行（3 个课时）· tasks 8 · qa 1 · keyframes 42
```

**结论**：上限今天不咬人；咬人的是「截断了不说」与「没有检索」。方案因此按这个优先级排。

### 1.4 可以直接复用的既有约定

- **唯一的课程搜索谓词**：`shared/course-search.ts`（侧栏与全屏浏览页共用，注释里写明「两个界面用不同口径回答同一个词会被当成 bug」）——笔记搜索要有自己的谓词，但同一套纪律。
- **「分块 + 显式展开」**：`App.tsx` 的 `visibleCourses`（默认 150）+「显示更多（还有 N 门）」，M3-2 收口时定的约定（不引虚拟滚动）。
- **测试缝**：`tests/helpers/fake-app-bridge.ts` 的 `tasks.list` 等已可注水；`tests/components/note-viewer.test.tsx` 已覆盖笔记库渲染。

## 1.5 执行期修正（2026-09-18 批1 落地时）

- **关键词字段收窄为「课程名 / 教师 / 课时名」**（方案 §3 D3 写的是「课程名 / 教师 / 课时名 / **课程号**」）。落代码时按 D3 自己的原则（只搜列表里看得见的字段）复核了一遍：**笔记库从不显示课程号**（那是侧栏课程行与全屏浏览页的字段），搜课程号会命中一条看不见该串的行——正是 D3 要避免的「看不见的命中」。故去掉课程号，并在 IPC 测试里把这条钉住（搜教师命中、搜教室不命中）。
- **关键词过滤随批1 一起落**（方案里属批2）：SQL 与总数在同一个 WHERE 子句里，分两批改会把这段 SQL 写两遍。批2 只补 UI（搜索框 / 空态 / 自动展开）。

- **批2 落地时测试抓到一个真 UX 缺口**：搜索零命中时，NoteViewer 走的是「尚无笔记」那条空态分支——**搜索框会跟着消失**（用户没法清空查询 = 死路），而且「尚无笔记」错误暗示库里一条都没有。修法：搜索中即使零命中也渲染列表本体（`library.length > 0 || searching`），空态由 NoteLibrary 自己给一行「没有匹配的笔记」。这正是「先写测试」的价值：不写这条断言，这个死路只能等用户在真实使用中撞上。

## 2. 方案

### 批1 — 契约：从「数组」到「能说实话的列表」

`notes:list` 与 `tasks:list` 的返回改成带总数的结构（**默认行为不变**，仍取最近 N 条）：

```ts
// src/shared/bridge.ts
list(query?: { keyword?: string; limit?: number; offset?: number }):
  Promise<ApiResult<{ items: NoteIndexInfo[]; total: number; limit: number }>>
```

- `total` = 满足条件的**总数**（不含 limit），UI 由此能写实：`共 12 条` / `显示最近 200 条（共 431 条）`。
- 主进程：`SELECT COUNT(*)` + 原查询（两条 SQL，同一个 WHERE 子句由一处拼装，避免口径漂移）。
- 界面上把硬编码的「最近 200 条 / 最近 50 条」换成**由数据算出来的**口径；**被截断时补一句出路**（如「更早的笔记可在左侧课程树里按课程打开」）。
- 这是**契约变更**：`bridge.ts`、preload、`ipc.ts`、两处调用点 + 钉住测试一起改（仓库纪律：改契约必落钉住测试）。

### 批2 — 笔记库搜索

- 新增 `shared/note-search.ts` 的 `noteMatchesQuery(entry, query)`：**只匹配列表里看得见的字段**（课程名 / 教师 / 课时名 / 课程号）——搜「教室」却命中一条不显示教室的行，用户会当成 bug（这是 D3）。
- 主进程按 `keyword` 做 SQL `LIKE` 过滤（**不是**渲染层过滤已取回的 200 条——那等于对 200 条以外的笔记撒谎）。
- `NoteLibrary` 顶部加搜索框（复用 `.search-input` 样式）+ 命中计数；无命中给一行空态（复用 `.msg`）；搜索时**自动展开命中的分组**（否则用户搜到了却看不见）。
- 搜索框的口径写进 placeholder（如「搜索笔记：课程 / 教师 / 课时」），与侧栏课程搜索的措辞风格一致。

### 批3 — 分页（「显示更多」）

- 沿用 M3-2 约定：列表初始渲染 N 条（笔记库按**行**计，默认 100），底部「显示更多（还有 M 条）」；`offset` 走批1 的契约。
- 分组视图与分页的交互：分页作用在**过滤后的行集**上，再分组——保证「显示更多」不会让某个分组悄悄变长而不刷新。
- 任务列表（50 条）同款。

### 批4 — 文档与台账

PROGRESS / README（若测试数变）/ CHANGELOG [未发布]；`docs/skills/ui-layout/SKILL.md` 不必改（本方案不涉排版），但**新增的列表契约与「不静默截断」纪律**要写进 `docs/skills/note-craft/SKILL.md`（笔记库属于笔记链路）。

## 3. 决策点（每条都给推荐）

| # | 决策 | 推荐 | 理由 / 备选 |
|---|---|---|---|
| **D1** | 是否改 `notes:list` / `tasks:list` 的返回结构 | **改**（返回 `{ items, total, limit }`） | 不改就无法如实告知总数；bridge 是内部契约且有钉住测试，改动可控。备选：只加 `limit` 参数不改返回（省事，但「截断了」这件事仍然说不出口） |
| **D2** | 过滤在主进程还是渲染层 | **主进程 SQL** | 渲染层过滤只能过滤已取回的 200 条——用户搜「某节课」搜不到，而那条笔记其实存在，这是**对数据撒谎**。数据量（每课时 1 行）也完全撑得住 |
| **D3** | 笔记搜索的口径 | **只匹配列表可见字段**（课程/教师/课时/课程号） | 与 `courseMatchesQuery` 的教训同源但结论相反：课程树里教室/学期是可见的（所以该搜），笔记库里它们不可见（所以不该搜）。备选：直接复用 `courseMatchesQuery`（要额外把教室等字段塞进 NoteIndexInfo，代价更大且会搜出"看不见的命中"） |
| **D4** | 是否顺带任务/追问列表 | **任务一起做，追问留后续** | 任务列表同样是「最近 50 条 + 硬编码文案」的全局入口；追问是**按课时**的，50 条一节课基本够（真不够时它会先以「一节课 50 轮问答」暴露出来） |
| **D5** | 分页方式 | **显示更多（M3-2 约定）** | 虚拟滚动是明确不做项（2026-09-13 方案 §7）。初始 100 行 + 显式展开，与课程树一致 |
| **D6** | 搜索框位置 | **笔记库顶部，跟着「全部笔记」小标题走** | 与全屏课程浏览页的搜索框同款位置（那页也是标题行下一条搜索） |
| **D7** | 是否顺带做笔记库的筛选/排序（学期/来源/健康度） | **不做** | 记入候选。健康度筛选的正确落点是「体检」而不是列表筛选（现在体检入口在笔记页顶部，按课时给结论） |

## 5. 验收

1. **契约钉住测试**：`notes:list` 返回 `{ items, total, limit }`；`total` 大于 `items.length` 时 UI 必须出现截断提示（负向红线写成正向断言）。
2. **搜索口径测试**：`noteMatchesQuery` 对课程名/教师/课时名/课程号命中，对**教室/学期**不命中（钉住「只搜可见字段」这条决定）。
3. **主进程过滤测试**：`notes:list({ keyword })` 在 fake DB 上只回命中行，且 `total` 是**过滤后**的总数。
4. **实拍 + 探针**：`node scripts/ui-probe.mjs` 量搜索框宽度与命中计数位置；`ui-shots` 拍「搜索命中」「无命中」「截断提示」三态。
5. **不动的**：`courseMatchesQuery`（课程侧口径已定，不动）、笔记行/分组头的既有结构、`升级旧笔记` 与 `导出 Obsidian` 入口。

## 6. 明确不做

- **笔记正文全文检索**（`note_json` 里搜内容）：需要 FTS5 或全表 LIKE 扫描，收益与成本不成比例——用户找笔记靠的是「哪门课哪一讲」，不是正文里的某个词。记入候选。
- **虚拟滚动**（2026-09-13 §7 已明确不做）。
- **笔记库的筛选/排序面板**（D7）。
- **改变上限数值**（200 → 更大）：在批3 的分页到位之前，单纯放大上限只是把静默截断推迟，且一次渲染更多行会拖慢列表。
