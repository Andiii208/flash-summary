## 1. 背景与问题清单

### 1.1 封面被裁切（P26）

- **用户现象**：B 站课时的封面「被裁切过，不完整的」。
- **根因（渲染层一行规则）**：`style.css:2251-2258` 的 `.note-cover { width: 100%; max-height: 200px; object-fit: cover }` 把封面塞进 **640×200 = 3.2:1** 的盒子居中裁切。B 站封面是上传原图（view API 的 `pic` 字段，`src/main/bilibili/parse.ts:64`，实测约 1146×647 = 1.77:1）：渲染成 640×361 后垂直裁掉 161px（上下各约 80px），即 **44.4% 的图高被裁**。≤1024px 窄窗下 masthead 吃满内容盒（`style.css:1999`），盒子比例更极端（约 3.5–4.5:1），裁得更狠。
- **数据链路干净（不必动）**：`cover.ts:40-51` 的 `saveLessonCover` 原样落盘（无 jpeg-js、无 resize、无裁剪）；`fetchImageAsDataUrl`（`client.ts:194-213`）原样 GET，全仓无 `@宽w_高h` 后缀处理；最早关键帧兜底（`NoteViewer.tsx:212-223`）也是 ffmpeg 全分辨率原帧——**兜底帧同样被这个盒子裁**，所以即使看到的是兜底帧，裁切依旧来自 CSS 那一行。
- **同族三处（同批收口，见 D1）**：`.evidence-fig img` 用 `aspect-ratio: 16/9; object-fit: cover`（`style.css:2177`）会把 4:3 的 PPT 页裁掉；`.timeline-thumb img` 168×96（1.75:1）`object-fit: cover`（`style.css:1852-1853`）对 PPT 页有轻微裁切；B 站导入对话框预览 72×45 `object-fit: cover`（`style.css:2500-2508`）对 16:9 源约裁 10% 宽。
- **界面区分真假封面（顺带回答「是不是根本没抓到封面」）**：masthead 出现「重新获取封面」小按钮 ⇔ 没有落库封面、看到的是兜底帧（`NoteViewer.tsx:441-450`，条件 `coverDataUrl == null && courseSource === 'bilibili'`）；上一轮已落地 `notes:backfillCover` 回填通道（P1/D8），封面抓取失败这条路已经能自救。

### 1.2 导图无放大入口（P27）

- **用户现象/原话**：「思维导图的排版问题你解决了，但是我认为应该设置一个能够放大查看的功能，不然太小了影响观看」。
- **现状：能力在、入口无、倍率不可见**：
  - Ctrl/⌘+滚轮缩放：`MindMap.tsx:333-346`（裸滚轮=滚动，有测试钉住 `mindmap.test.tsx:244-254`，**别动**）；
  - 键盘 `+`/`=`/`-`/`0`：`MindMap.tsx:381-392`，绑定在画布容器 `onKeyDown`（`:559`）——**必须先点选画布获得焦点**；
  - 工具栏唯一的视图按钮「适应窗口」：`MindMap.tsx:462-464`，而 `fitToViewport` 是 `Math.min(1, Math.max(MIN_SCALE, …))`（`:253`）——**只缩不放**；
  - 全组件无任何缩放倍率渲染（无 `Math.round(view.scale*100)` 之类），快捷键说明只存在于画布的 `aria-label`（`:554`）。
- **为什么「太小」是真的**：默认窗 1266×738、内容 892×1028 时，笔记宿主画布内容盒 613×316 → `min(613/892, 316/1028)=0.307` 被 `MIN_SCALE = 0.4`（`MindMap.tsx:16`）钳住 → **首屏 scale = 0.400**（HEAD 实测，见 PROGRESS 批6 二次评审订正）；课程导图弹层宿主推算约 0.5 倍。用户看到的是一张缩到四五成的图，旁边没有一个可点的放大按钮。
- **两个宿主共用同一组件**（笔记页 `NoteViewer.tsx:553-564`、课程弹层 `CourseMapDialog.tsx:64`），工具栏加控件两处自动同时生效。
- **会撞的既有断言（只有一条）**：`tests/components/mindmap.test.tsx:112` 的按钮清单是**精确相等**断言（`['全部收起','展开 L2','展开 L3','全部展开','适应窗口','回忆模式']`），加按钮必须同步。

### 1.3 宽屏右侧空白（P28，等比例放大）

- **用户现象/原话**：「窗口放大占全屏的时候，软件界面右侧一大片空白……我认为可以直接等比例放大呀，这样可能相对会美观一些」。
- **上一轮修到哪一步**：`9a62003`（批6/P24）新增 `@media (min-width: 1600px)`（`style.css:2002-2019`）把**列表型页面**（任务历史/笔记库/近期追问）的 `--content-max` 帽放开；**阅读页按 D12 明示的纪律不动**（`.note-viewer` 阅读态 860 / `.note-body` 640）。所以 2560 窗口下：面板右缘 1188 → 右侧仍空 **1372px**；1920 下空 **732px**（元素右缘→视口右缘口径，含内容盒右侧 24px 内边距）。
- **本轮新测算（做缩放方案的前提）**：`setZoomFactor(z)` 后 **CSS 视口 = 物理宽 / z**——所有 `@media` 断点改按 CSS 视口判定。由此三个硬结论：
  1. 只要 z 让 CSS 视口 <1600，上一轮新增的宽屏档**整体失效**（2560@1.75 → 1463）；
  2. z 让 CSS 视口 <1024 还会**误触窄窗档**（1600@1.75 → 914）；
  3. **与批4 的追问坞直接互斥**：坞需要 CSS 视口 ≥1400 才放得下（算式见 §1.5），若缩放把视口钉在 1280，坞在任何窗口都进不了布局。
  - 结论：缩放公式必须与坞**联合定档**（D2）——推荐把 CSS 视口钉在 **1600**（而非 1280）：宽屏下坞永远常驻、空白被坞吸收、窄窗档永不误触、已删的 1600 规则也无复活空间。
- **档位测算**（联合公式 `z = clamp(W/1600, 1, 2.5)`，推导见批3；坞宽 = min(520, 视口−1008)、下限 340；空白 = 坞右缘→视口右缘的物理像素）：

  | 物理窗宽 W | z | CSS 视口 | 坞宽(CSS) | 右侧空白(物理) | 修前空白(zoom=1、无坞) |
  |---|---|---|---|---|---|
  | 1266（默认窗） | 1.00 | 1266 | 浮动形态 | — | 92 |
  | 1440 | 1.00 | 1440 | 432 | 0 | 252 |
  | 1600 | 1.00 | 1600 | 520 | 72 | 412 |
  | 1920 | 1.20 | 1600 | 520 | 86 | 732 |
  | 2560 | 1.60 | 1600 | 520 | 115 | 1372 |
  | 3840（4K） | 2.40 | 1600 | 520 | 173 | 2652 |
  | 5000（超帽） | 2.50 | 2000 | 520 | 1180 | 3812 |

  floor 步进保证 CSS 视口恒 ≥1280 的方案已废止（那版让坞永无落点）；连续公式 + 「|Δz|>0.02 才应用」把拖拽期重排降到约每 32px 一次。cap 以内 CSS 布局与 1600 宽窗口**逐像素同一**，物理等比例放大——这就是「视觉统一性」；cap 2.5 的已知边界：5000px 以上超宽屏空白回来（D2）。
- **风险面已摸底**：全仓零现有缩放能力（无 `setZoomFactor`/菜单 zoom role/快捷键）；主窗创建于 `src/main/index.ts:123-140`（无尺寸记忆、无 resize 监听先例）；`.dialog` 的 `86vh` 与自绘 overlay 的 `position:fixed` 在 page zoom 下物理占比不变（理论安全，**必须实拍，这是缩放方案能否成立的判据**——上一轮方案 §5 原话）；`printToPDF` 用主窗 webContents（`pdf-export.ts:27`），zoom≠1 会把讲义版式按倍率缩放、A4 分页错乱——**必修项**（保存/恢复 zoom）；登录窗（`cas-login.ts:293-304`）不缩放；PDF 打印本就整体隐藏 `.app-shell`（`print.css:24-26`），坞挂在 `.app-shell` 内自动不进 PDF。

- **所以这是新功能**。行内 `==高亮==` 的完整实现面（现状 → 缺什么）：
  1. 解析：`md-lite.ts:43` 的 `parseInline` 只认 `**`/`` ` ``/`$`（`md-lite.ts:18-23` 类型联合四种 token）——不认 `==`，今天模型若输出会**印字面符号**（与批5 P18「字面反引号」同型病）；
  2. 渲染：`MdLite.tsx:38-49` 无 `<mark>` 分支；
  3. 样式：`style.css`/`print.css` 无 mark 底色规则（`printBackground: true` 已有，能印）；
  4. 投影判据：`views.ts:137-148` 的 `looksLikeMarkdown` 不认高亮（判据只有一份，就在 views.ts）；
  5. 模型侧：`summarize.ts:48` 的 prompt 规约第 4 条**明令禁止一切行内 Markdown 标记**；放开需同步 `CURRENT_PROMPT_VERSION` +1（`schema.ts`）→ 触发全库「升级旧笔记」建议（**不强制、不回溯旧笔记**，要点明代价）；
  6. 导出口径：`obsidian.ts:134`/`:156` 原样直通 overview/methodology——Obsidian 原生恰好把 `==text==` 渲染成高亮，直通即可，但三端口径要写进 SKILL §9（否则「屏幕印符号、Obsidian 显高亮」的漂移会被人当 bug 报）。

### 1.5 追问的定位与门禁（P36/P37）

- **用户现象/原话**：「默认窗口大小的时候，右边其实还是有部分空白的，整体布局不是特别协调……可以把上面的追问栏给挪到右侧去，采用一个固定位置的悬浮对话窗，这样可能更方便用户去针对笔记进行提问，同时也可以占据空白位置，让布局更加协调」+「现在的追问我看好像还设置了没有笔记也可以问答的功能，我认为这个是没有必要的，还不如直接去问网页 AI 呢，所以我觉得可以只留着这个针对笔记内部的追问对话栏」。
- **现状（截图目视 + 代码核对）**：
  - 追问是顶部第四个 tab（`App.tsx:36` `MainTab` 四值、`:44-49` `TAB_LABELS`、`:676-690` `tab === 'qa'` 挂载 `QaPanel`）——读笔记时提问必须切 tab，笔记被整页替换；
  - 默认窗 1266×738 下（你截图的状态）：侧栏 304 + 内容盒内边距 48 + `.note-viewer` 帽 860 = 右缘 1188，**面板帽内正文列 640 右侧还空 220px、帽外还空 78px**——这就是「默认窗也有空白、布局不协调」的实体；
  - `QaPanel` 的问答能力完整（对话流 / 失败重试驻留 / busy 提示 / LessonChip 切课时 / 近期追问空态，`QaPanel.tsx:53-179`），缺的只是**摆放位置**；
  - CSS 现状：`.qa-panel` 等统一吃 `--content-max: 860` 帽（`style.css:614`、`:1512`、`:1516`）。
- **「无笔记也能问」的两处实锤（P37）**：
  - 主侧：`ipc.ts:2001-2023` 的 `qa:ask` 只要求 lessonId 合法，note 行查不到时 `note = null` 照常组装上下文；`qa.ts:67-74` 明确写着「无笔记**且**无转写 → 仅可回答不依赖课时材料的一般性问题」；
  - 渲染侧：`App.tsx:1729-1732` 问前弹一句 info toast「该课时尚无笔记，回答不基于笔记内容」然后照发；`QaPanel.tsx:77/159` 的空态与 placeholder 也明说「也可以直接提问」。
- **右坞的布局算式（可行性核心）**：坞进布局需要 `CSS 视口 ≥ 304(侧栏) + 24 + 640(正文列) + 16(间距) + 340(坞最小宽) + 24 = 1368`——取整为断点 **1400px**。≥1400 时常驻坞（flex 子项，宽 `min(520, 视口−1008)`，把右侧空白全部吸收）；<1400（含默认窗 1266）时退化为**固定位置悬浮窗**（`position: fixed` 右侧贴底、可折叠）——这就是你說的「悬浮对话窗」，且两种形态共用同一个组件与同一套 CSS 类。
- **与缩放的联动（已并入 D2/批3）**：缩放公式改为把 CSS 视口钉在 1600（§1.3 表），宽屏下坞永远常驻；若按旧稿钉 1280，坞在任何窗口都进不了布局——两功能必须同批协调，不能各做各的。

## 3. 决策项（D1–D10，均给推荐；Andiii 习惯「按推荐」拍板）

- **D1 — 封面裁切修法**。推荐：**`aspect-ratio: 16/9` + `object-fit: cover` + `max-height: 340px`**（B 站封面实测 16:9 → 零裁切且铺满 640 列；异形封面轻微裁切），同族三处（证据图/时间线缩略图/导入预览）同批同口径。备选 A：`object-fit: contain`（永不裁，但 16:9 图在宽盒里两侧留色带、横幅观感变小）；备选 B：`height: auto` 不限高（封面最高占首屏约 45%，可能挤掉章节 chips，需实拍回购）。
