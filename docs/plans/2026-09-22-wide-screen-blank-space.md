## 0. TL;DR

- **实测定性**：最大化后窗口物理宽 2560（用户屏 2560×1600、DPI 150%），窗口缩放把 CSS 视口
  钉在 1600，字号被放大约 1.6 倍，**但空白被等比例放大成 632 CSS px ≈ 1011 物理 px，
  占窗口宽度约 40%**；坞展开后仍剩约 350 物理。窗口化时填充率反而更高（约 76%）。
- **不止主界面**：「我的学习」全屏弹层 `width: min(1100px, 96vw)` 封顶，宽视口下两侧
  各 ~216 CSS px（≈346 物理）遮罩空白；「全部课程」1440 封顶两侧各 ~80 CSS。**这两个
  「全屏」界面本身就是「全屏里一半空白」。**
- **根因**：不是 bug——P28「视口钉 1600 + 布局只为 ≤1600 设计 + 列宽列数固定」的组合，
  缩放放大了内容也同步放大了空白；弹层则是固定 px 封顶的旧策略。
- **终局（推荐）**：640 阅读轴与缩放机制不动，把空白变结构——**笔记页正文在坞槽预留区
  居中 + 追问坞从「悬浮聊天框」升格为「笔记副驾驶面板」（追问/目录 tab、宽屏不自动
  收球、高地档、空态建议问题）、任务页卡片弹性双列、设置页两栏化、两个全屏弹层解除
  px 封顶改随视口，且「我的学习」内部两栏**；目标各页签内容填充率 **≥91.5%**，剩余
  留白对称为「呼吸区」，窗口化↔最大化连续过渡无跳变阈值。
- **关于追问悬浮小球+小窗口（Andiii 三问）**：更好的不是换形态而是**升格**——四路线
  评估见 §6.0，右列化（VS Code 式）不更省地方且要推翻你两条自令、只列为 D11-B 不默认
  推；默认走 R1+（tab/宽屏常显/高地档/建议问题），折叠态 430px 空白问题同步消失。
- **决策项**：D1 主线路、D2 正文列居中/放宽、D3 坞内 tab 合并目录、D4 任务页 Outlook
  右辅列（缓）、D5 宽屏钉子（本方案不需推翻）、D6 验收线、D7 建议尺寸提示、D8 弹层
  同步解除封顶、D9 sticky chips 去留、D10 是否修 DPI 语义/display-metric 机制漏洞、
  D11 追问坞形态路线（R1+/R2/R3，推荐 R1+）、D12 坞小特性（建议问题/答案全宽）。
  **另请确认「全屏」口径**（最大化 /「我的学习」弹层 / 两者都是，§1.1）。

### 1.3 现行机制与 zoom 语义锁定*(v2 新增实测)*

`z = clamp(W_phys / 1600, 1, 2.5)`（`src/main/window-zoom.ts`），`W_phys =
win.getContentBounds().width`，zoom 后 CSS 视口 = `W_phys / z`。
**语义实验**（2026-09-22 `.tmp-zoom-check.mjs`：PowerShell `SetWindowPos` 设窗口物理宽，
量 `innerWidth` 反推）：

| 设置窗物理宽 | innerWidth | 反推 | 结论 |
|---|---|---|---|
| 1000 | 986 | z=1（(1000−14)/986=1.000） | `getContentBounds().width` **物理语义**（DIP 语义会得视口 1500） |
| 1280 | 1266 | z=1.000 | 同上 |
| 1500 | 1486 | z=1.000 | **若 DIP 语义视口应为 2250，实测 1486 ⟹ 物理** |
| 2560 | 1600 | z=1.591（cap 未触顶） | 1600 钉住 ✓ |

附带发现：**zoom=1 时 devicePixelRatio=1.5、1 CSS px=1 物理 px**——DPI 1.5 屏上窗口化
状态字号 = 15 CSS px = 15 物理 px = **10pt**；最大化 z=1.6 时 = 24 物理 = 16pt。
**「未全屏 vs 全屏」的断层是双重的：空白占比 24%→40%，字号 10pt→16pt。** 字号断层是
P28 的明文取舍（「窗口窄于基准时不缩小界面」），保留不动（见 §7 D10 的机制修复只修
语义漂移，不改基准）。

| 窗口物理宽 | zoom | CSS 视口 | 内容列占用 | 笔记页右空白（CSS） | 右空白物理 | 占窗宽 | 坞展开后剩余 |

## 2. 根因（四层）

1. **视口恒 1600（P28 锚）**：`z = W/1600` 使 ≥1600 物理宽的窗口视口恒 1600，布局永远
   「看不见」真实窗口更大。
2. **布局只为 ≤1600 设计**：面板轴 860、正文轴 640、侧栏 304 全固定；宽屏方向零断点
   是 P28 主动决策（`tests/style-scale.test.ts:206` 钉死），其理由「宽屏档在缩放方案下
   永不可命中」逻辑成立，但也顺带封死了「视口 >1600 时填充内容」这条唯一出路。
3. **DPI 错位放大器**：设计基准 1600 是「DPI 100% 屏的 1600 CSS px」；用户屏物理 2560
   = DIP 1707×1.5。缩放把 1600 设计宽拉到 2560 物理换字号可读（15→24 物理=16pt，合理），
   **40% 空白同步拉大 1.6 倍**——缩放对内容是正义，对空白是放大器。
4. **弹层旧策略**：固定 px 封顶（1100/1440）诞生于无缩放的年代，视口涨到 1600 后
   封顶值不再等于「视口−呼吸边」，于是「全屏弹层自带黑边」。

### 2.1 机制层隐藏漏洞：ZOOM_CAP 触顶后视口不再钉 1600*(v2 新增)*

`z = min(2.5, W/1600)`：当 **W > 4000 物理**（4K/双屏横拼拖窗）时 z 触顶 2.5，视口
= W/2.5 **> 1600**——布局会第一次「看见」>1600 的视口，而它没有任何定义，右侧空白
= (视口−968)×2.5 物理 px，用户拖到双屏会看到「越拖越空、空到失控」。
**P28 钉子注释「宽屏档永不可命中」是假命题（cap 之上会命中）**——本方案不改钉子
（本机 2560 触不到），但把这条写进 `window-zoom.ts` 注释订正 + 作为批4 机制收口项，
避免下个会话据此注释做错误推理。

### 2.2 机制层缺口：DPI 变化不重算 zoom*(v2 新增)*

`src/main/index.ts` 只监听 `resize`；换显示器（不同 DPI）、改系统缩放、RDP 远程切换后
窗口 DIP 宽不变而物理宽变，zoom 不重算 → 跨屏拖动时字号/空白比例漂移。**未实测复现
（本机单屏 1.5），列为风险项，批4 用一次「改系统缩放→重启」的人工走查确认；若复现，
加 `display-metric-changed` 监听（3 行内小修，不动公式）。**

## 3. 业界调研（2026-09-22 WebFetch 实证 + 通行模式）

### 3.1 微软官方：宽屏的正确姿势是「放更多内容」，不是「放大同样内容」

WinUI 官方 *Responsive design techniques*（learn.microsoft.com/windows/apps/design/
layout/responsive-design）原文引用：

> "If you design an app to look good on a device that has a small screen ... it will be
> usable on a PC with a much bigger display, but there will probably be **some wasted
> space**. You can customize the app to **display more content when the screen is above a
> certain size** ... **By putting more content on the screen, you reduce the amount of
> navigation the user needs to perform.**"

六技术：Reposition（重排）/ Resize（伸缩边距与内容框）/ Reflow（加列换流）/ Show-hide
（显隐与元数据分级）/ Re-architect（list-detail 重构）/ Adaptive（断点换布局）。
本例空白 40% 属「wasted space」标准病例，处方 = Reflow + Show-hide + Re-architect。
**Resize 被排最次要且明指「调边距与内容框尺寸」而非「放大字号」。**

### 3.2 排版科学：行宽上限允许正文列从 640 放宽，但中文要克制

Wikipedia *Line length*：屏幕阅读共识 45–75 字符/行、理想 ~66；「55 cpl 是速度/理解
折中」；CSS 实践 `66ch`。当前 640px/15px = 42.7 全角字/行（仓库实测）处区间下沿；
放到 800px=53.3 字、880px=58.7 字仍在区间内；中文混合内容 50 字左右是安全值。
**但 640 是 SKILL §6 钉死的舒适区折中，是否放宽由 D2/D3 裁（本方案默认不动 640）。**

### 3.3 通行产品模式（宽屏「吃空白」的四种成熟答案）

| 模式 | 代表 | 做法 | 适用性 |
|---|---|---|---|
| 工作台拉伸 | VS Code | 容器模型，编辑区拉伸填满；2024 年起官方 Secondary Side Bar 把 Terminal/Problems 拖右栏 | 任务页天然适合 |
| 阅读宽开关 | Obsidian | 官方 *Readable line length*：长文限宽、可切 Full width；内容区随窗拉 | 印证「640 钉住 + 辅列」 |
| 双栏阅读 | 语雀 / 飞书文档 / GitBook | 正文定宽**居中** + 右侧固定目录列，填充率 ~90%，留白对称 | 笔记页最值得抄 |
| 三栏工具 | Outlook / MarginNote | list + reading + detail，宽屏放更多信息 | 任务页右辅列（D4，缓） |

共性：**没有成熟产品在宽屏存 40% 空白**；拉伸、加列、居中装订线可组合。

## 4. 设计原则与红线

1. **640 阅读轴不主动动**；凡动笔记页几何，P47 双态十项复跑为硬门槛
   （`.zcode/p47-compare.mjs` 手法）。
2. **缩放保留**：物理字号 = 15px CSS × z 由窗口物理宽决定，是 DPI 1.5 屏可读性根基；
   改动只发生在视口之内的布局。
3. **连续过渡**：新布局参数一律 `clamp() / minmax() / calc()` 连续函数；窗口化↔最大化
   无阈值跳变；1180/1024 窄向断点不动。
4. **token 纪律**：间距/圆角/字号只取 SKILL §1 刻度，新野值即红。
5. **测试只增不减**：几何断言改写进 `style-scale.test.ts` / `ui-probe`，不删断言。
6. **弹层分治**：主界面「填」（内容填充），modal 类弹层「居中+自适应边」；「我的学习」
   「全部课程」是「界面」不是 modal，按填处理（解除 px 封顶）。

## 5. 候选方案对比

| 方案 | 思路 | 填充率（1600 视口） | 改动面 | 风险 | 结论 |
|---|---|---|---|---|---|
| 甲·内容弹性 | 面板轴弹性、卡片双列、首页加宽 | ~75% | 小 | 低 | 采纳为主干 |
| 乙·右栏辅列 | 右目录列、任务 list-detail、设置两栏 | ~90% | 大 | 中 | 拆分：目录并入坞优先，任务右列缓议 |
| 丙·居中装订线 | 正文居中、留白对称 | 不改占比改观感 | 极小 | 低 | 采纳为乙的视觉层 |
| 丁·zoom 公式改革 | 视口=窗口宽、全响应式（推翻 P28） | ~95% | 巨大 | 高 | **不采纳**：推翻 P28/P36 与全部 ≤1600 假设，收益甲+乙可达 |

**不选丁的理由**：字号锚与视口锚要拆开重推，`window-zoom.ts` 基线、
`style-scale.test.ts` 宽屏钉子、全部页面假设、`pdf-export.ts` 的 zoom 复位都要动；
甲+乙 已能把空白从 40% 压到 ≤15%，余量用丙消化。最小改动解决最大别扭。

## 6. 推荐终局（分页签几何，视口 1600 / 最大化口径；数字统一为
「内容填充率 = (侧栏 + 内容占用 + 左右边距) / 视口」）

内容盒 = 1600 − 304（侧栏）− 24×2（.content padding）= **1248**；右缘 24 即呼吸边。

#### 6.0.1 四条路线横向对比（视口 1600 / 最大化口径）

**一句话回答你的问题**：更好的排版不是换形态，是**升格**——把右缘从「一个会折叠的聊天
框」升级成「这篇笔记的副驾驶面板」（追问 + 目录两个 tab、宽屏常显、空态有建议问题），
 blank 从 40% 压到 ≤12% 且折叠态 430px 空白问题同步消失。右列化（R2）我做过诚实评估：
它并不更省地方，且要推翻你两条明确的自我约束，所以只列为选项、不塞进默认路线。

#### 6.0.2 R1+ 三升格定义（并入批2）

1. **tab 化**：坞头「追问 | 目录」两个 tab（D3）。目录 = 现有 chapter chips 升级为可点
   目录列表（数据已在 `NoteViewer`，只读传入）。追问 tab 保持现值（气泡 + 输入行）。
   aria：`role="tablist"` + `aria-selected`；切 tab 不触发收球。
2. **宽屏不自动收球**：`use-qa-dock-at-hero` 的 auto 分支加视口判据——视口 ≥1500 CSS 时
   auto 视同 open（宽屏右侧本就是结构区，无需保护 hero 也无需球）。折叠只剩手动
   （收球键照旧 44px 右缘）。**P47「展开/折叠零布局变化」原样成立**（槽位常驻不动）。
   附带收益：v2 §6.1 交底的「折叠态 430px 空白」在宽屏不再出现（只剩手动折叠场景）。
3. **高地档 + 空态**：高从 min(56vh,560) 升为**视口感知** `clamp(300px, min(70vh, 680px),
   内容区高-32px)`——化解「P47 嫌短 / P50 嫌大」的两头拉扯（宽屏桌面大可更高、上限仍封，
   输出后不再「变大」因为高度不再内容驱动）。空对话态给**建议问题 chips**（由
   `note.chapters` 标题/摘要现成数据生成 2–3 个，如「XX 的结论是什么？」），点一下即问——
   空坞从「空」变「入口」。长答案可读性用「气泡全宽查看」补偿（气泡双击 → 复用
   `.fullscreen-overlay` 基元开一层大图式查看，z-index 40、Esc 关）——R3 卖点的平替。
